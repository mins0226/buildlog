# 빌드로그 2026-08-16

## 이번 주 만든 것

이번 주는 company-analyzer의 데이터 소스 안정화에 집중한 한 주였다. 기존에 쓰던 yfinance(무료 비공식 API)가 트래픽이 늘면서 429(레이트리밋)를 자주 뱉기 시작했고, 처음엔 캐시 확대와 재시도 백오프로 땜질했지만 근본적으로 부족해서 curl_cffi로 TLS 지문을 위장해 우회하는 방법까지 시도했다. 그래도 불안정해서 아예 공식 유료/무료 티어가 있는 Financial Modeling Prep(FMP) API로 데이터 소스를 통째로 교체했는데, 이번엔 무료 티어 쿼터가 너무 빠듯해서 peer 조회를 줄이고 캐시 TTL을 크게 늘리는 등 쿼터 절약에 시간을 썼다. 결국 이런저런 트레이드오프를 따져본 뒤 다시 yfinance로 롤백하는 걸로 이번 주를 마무리했다 — 왔다갔다한 것처럼 보이지만, 각 옵션의 실제 한계(레이트리밋 vs 쿼터 vs 안정성)를 실측으로 확인한 뒤 내린 선택이다. 동시에 공개 데모용으로 예시 티커 칩, 로딩 스피너, 파비콘, 콜드스타트 방지용 GitHub Actions 워밍업 잡을 추가해 처음 들어온 사람도 바로 써볼 수 있게 다듬었다.

- LabMate 실사용자 테스트 — ❌ 안 함 (이번 주 커밋 없음)
- macro-analyzer를 일회성 스크립트에서 정기 리포트 파이프라인으로 연결 — ❌ 안 함
- company-analyzer 대시보드 실사용 중 불편한 지점 정리해서 반영 — ✅ 완료 — 데이터 소스 안정화 + 예시 티커/로딩/파비콘/콜드스타트 워밍업 등 데모 완성도 개선

## 배운 것

- 무료 데이터 API를 교체할 때는 "이론상 더 안정적"이라는 이유만으로 옮기면 안 된다 — FMP로 갈아탄 뒤에야 무료 쿼터가 실사용 트래픽엔 턱없이 부족하다는 걸 알았고, 결국 원래 쓰던 yfinance로 돌아왔다. 다음엔 옮기기 전에 무료 티어 쿼터 한도부터 숫자로 확인하는 게 먼저다.
- 레이트리밋 문제는 캐시 확대 → TLS 우회 → 소스 교체 순으로 점점 무거운 해법을 시도하게 되는데, 결국 가장 가벼운 해법(캐시+백오프)의 한계를 명확히 아는 게 다음 단계 판단에 도움이 됐다.
